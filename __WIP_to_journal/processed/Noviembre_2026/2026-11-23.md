# 2026-11-23 — Escenario sintético de sushi e inventario del esquema de Odoo

## 1. Objetivo de la sesión

La sesión se ha centrado en preparar la base técnica para construir los datos sintéticos del TFG sobre Odoo 19 Community. Se ha comprobado el acceso a Odoo, se ha avanzado en la definición del escenario de negocio, se han extraído los metadatos del ORM y se ha contrastado el esquema físico de PostgreSQL para los modelos relevantes.

El resultado principal es un inventario estructurado de modelos, campos, relaciones, módulos, tablas y restricciones, junto con tres scripts Python y un libro Excel de consulta. También se ha documentado el trabajo en el Journaling y se ha publicado en GitHub.

No se han creado todavía los registros sintéticos del escenario en Odoo. El trabajo de hoy prepara y verifica el esquema necesario para hacerlo posteriormente mediante la API JSON-2 y el ORM.

## 2. Comprobación de Odoo y de la API JSON-2

Se ha trabajado con la instancia local de Odoo 19 Community:

- URL: `http://localhost:8069`.
- Base de datos: `Odoo-tfg`.
- Contenedores Docker: `odoo-tfg` y `odoo-tfg-db`.
- PostgreSQL: versión 17.

Se ha comprobado que Odoo responde y que la API JSON-2 está disponible. La primera consulta de autenticación falló porque la variable de entorno `ODOO_API_KEY` estaba vacía y devolvió `401 Unauthorized`. Tras configurar la clave en el entorno, la autenticación funcionó correctamente.

Se ejecutó una consulta de lectura sobre `purchase.order` mediante `search_read`. La respuesta permitió recuperar pedidos de demostración como:

- `P00011`, proveedor Ready Mat.
- `P00010`, proveedor Azure Interior.
- `P00009`, proveedor Gemini Furniture.
- `P00008`, proveedor Wood Corner.
- `P00007`, proveedor Ready Mat, en borrador.

Estos registros se utilizaron para comprobar la conexión y explorar el comportamiento de la API. Se mantienen como datos demo y no se modifican para construir el escenario principal.

También se consultaron los campos de `res.partner` mediante `fields_get` para identificar los atributos disponibles para contactos: nombre, referencias, tipos de contacto, datos de dirección, VAT, estado activo, idioma, etiquetas, compañía y relaciones.

## 3. Decisión y orientación del escenario sintético

Se ha revisado el escenario inicialmente planteado con entidades de mobiliario y se ha orientado el conjunto de datos principal a un fabricante y distribuidor de sushi. El objetivo es disponer de productos alimentarios y relaciones de negocio que permitan representar una incidencia transversal entre Compras, Inventario, Fabricación y Ventas.

Se mantiene la decisión de:

- No crear una compañía nueva.
- No modificar los datos de demostración existentes.
- Crear entidades sintéticas diferenciadas mediante referencias con prefijo `TFG-`.
- Reutilizar la compañía, el almacén y la infraestructura existente cuando resulte adecuado.
- Construir los registros a través de la API JSON-2/ORM, respetando los flujos estándar de Odoo.

Entre las materias primas y componentes considerados para el escenario están el salmón, el arroz, el alga nori, el aguacate y el queso crema. Se han definido referencias para identificar proveedores y clientes sintéticos, entre ellas `TFG-PROV-001`, `TFG-PROV-002`, `TFG-CLI-001` y `TFG-CLI-002`.

La incidencia de referencia gira en torno al suministro de una materia prima —salmón— y sus efectos sobre las existencias, la fabricación y los compromisos con clientes. La definición detallada de cantidades, documentos, relaciones y variantes de evaluación deberá mantenerse coherente con la estrategia de datos de prueba del proyecto.

## 4. Extracción de metadatos del ORM de Odoo

Se han extraído los metadatos de Odoo mediante la API JSON-2, consultando los modelos internos:

- `ir.model`: catálogo de modelos.
- `ir.model.fields`: definición de campos.
- `ir.module.module`: módulos instalados.
- `ir.module.module.dependency`: dependencias entre módulos.

Los resultados se han guardado como JSON en:

`~/odoo-tfg/data/odoo_schema_inventory/raw/`

Archivos obtenidos:

| Archivo | Contenido | Registros |
|---|---|---:|
| `ir_models.json` | Modelos registrados | 469 |
| `ir_model_fields.json` | Campos registrados | 9.205 |
| `installed_modules.json` | Módulos instalados | 77 |
| `module_dependencies.json` | Dependencias de módulos | 1.482 |

Se ha comprobado que los cuatro JSON son válidos y se han revisado muestras de sus estructuras. Se han identificado, entre otros, los metadatos de módulos que participan en la definición de modelos y campos, así como los atributos que describen las relaciones entre modelos:

- `relation`: modelo relacionado.
- `relation_table`: tabla intermedia de relaciones Many2many.
- `column1` y `column2`: columnas de la tabla relacional.
- `modules`: módulos que participan en la definición del modelo o aportan el campo.

Esta información permite describir el modelo lógico de Odoo sin confundirlo con las tablas físicas de PostgreSQL.

## 5. Delimitación del alcance funcional

Se ha definido una lista explícita de 34 modelos principales para el TFG, centrados en Productos, Compras, Inventario, Fabricación y Ventas.

Los 16 módulos funcionales considerados son:

- `product`, `uom`.
- `purchase`, `purchase_stock`, `purchase_mrp`.
- `stock`, `stock_account`.
- `mrp`, `mrp_account`.
- `sale`, `sale_management`, `sale_stock`, `sale_mrp`.
- `product_expiry`, `mrp_product_expiry`, `sale_stock_product_expiry`.

El cierre transitivo de dependencias de esos módulos comprende 37 módulos: los 16 funcionales y 21 dependencias técnicas adicionales. La instalación completa contiene 77 módulos.

A partir de los 34 modelos principales se han incorporado los modelos relacionados directamente, sin expandir recursivamente todas las relaciones. El resultado del análisis es:

| Elemento | Resultado |
|---|---:|
| Modelos principales | 34 |
| Modelos relacionados directamente | 83 |
| Modelos seleccionados | 117 |
| Campos de los modelos principales | 2.456 |
| Campos de los modelos relacionados | 2.083 |
| Campos totales | 4.539 |
| Campos relacionales (Many2one, One2many y Many2many) | 1.572 |

La selección distingue los modelos que forman parte del alcance funcional del TFG de los modelos relacionados que se incluyen para entender las dependencias y relaciones necesarias.

## 6. Inspección del esquema físico de PostgreSQL

Se ha utilizado DBeaver para consultar el catálogo de PostgreSQL en modo de solo lectura. La inspección se ha limitado a las estructuras físicas relevantes para los 27 modelos/tablas principales seleccionados.

Se han exportado ocho CSV a:

`~/odoo-tfg/data/odoo_schema_inventory/sql_exports/`

Los ficheros son:

1. `1-id_conexion.csv`: base de datos, usuario y versión de PostgreSQL.
2. `2-inventario_tablas.csv`: inventario de tablas.
3. `3-id_27_tablas_principales.csv`: identificación de las 27 tablas seleccionadas.
4. `4-diccionario_columnas_sql.csv`: columnas, tipos SQL, nulabilidad y valores por defecto.
5. `5-claves_primarias_pk.csv`: claves primarias.
6. `6-claves_foraneas_fk.csv`: claves foráneas y reglas de actualización/eliminación.
7. `7-restricciones_sql_check_unique_exclusion.csv`: restricciones CHECK, UNIQUE y EXCLUSION.
8. `8-indices_unicos.csv`: índices únicos.

Los resultados de la auditoría de estos CSV son:

| Elemento | Resultado |
|---|---:|
| Tablas del inventario general | 549 |
| Tablas principales inspeccionadas | 27 |
| Columnas exportadas para las tablas seleccionadas | 853 |
| Claves primarias | 27 |
| Claves foráneas | 291 |
| Restricciones CHECK | 11 |
| Restricciones UNIQUE | 6 |
| Restricciones SQL en total | 17 |
| Índices únicos en total | 34 |
| Índices de clave primaria | 27 |
| Índices únicos no PK | 7 |
| Índices únicos independientes | 1 |

Las 27 tablas principales tienen una clave primaria simple basada en la columna `id`; no se han encontrado claves primarias compuestas en ese conjunto.

El único índice único independiente identificado por la auditoría es `product_product_combination_unique`, definido como índice parcial. Los otros seis índices únicos no PK están asociados a restricciones UNIQUE.

La inspección SQL se ha utilizado para contrastar el esquema físico y documentar restricciones, no para crear o modificar datos. Se mantiene la decisión arquitectónica de que los agentes y scripts de generación accedan a Odoo mediante JSON-2/ORM, sin escrituras directas en PostgreSQL.

## 7. Preparación del entorno Python

Para generar el libro Excel se ha preparado un entorno virtual en:

`~/odoo-tfg/.venv`

La primera creación del entorno falló porque el sistema no tenía instalado el paquete `python3.14-venv`, necesario para disponer de `ensurepip`. También faltaba `openpyxl`.

Se resolvió la incidencia completando primero la configuración pendiente de paquetes con `sudo dpkg --configure -a`, instalando después `python3.14-venv` y creando de nuevo el entorno virtual.

Con el entorno activado se instaló `openpyxl` (versión 3.1.5). La instalación quedó verificada y se utilizó para generar y comprobar el libro Excel.

## 8. Scripts de análisis y generación

Se han organizado tres scripts en `scripts/odoo_schema_inventory/`:

| Script | Responsabilidad |
|---|---|
| `analyze_scope.py` | Analizar el inventario de modelos, campos, módulos y dependencias. |
| `reduce_scope.py` | Aplicar la selección de modelos principales y relacionados directamente y resumir el alcance. |
| `generate_workbook.py` | Consolidar los metadatos JSON y las exportaciones SQL en un libro Excel. |

Los scripts utilizan los JSON y CSV almacenados fuera del repositorio, bajo `~/odoo-tfg/data/odoo_schema_inventory/`. De este modo, el código queda versionado, pero los ficheros de extracción y el libro generado no se incorporan a Git.
